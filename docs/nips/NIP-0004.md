# NIP-0004: Public node / API standard — developer keys for app-layer writes

| | |
|---|---|
| NIP | 0004 |
| Title | Public node & API auth standard |
| Status | Active |
| Created | 2026-07-04 |

## Rule

A public NetCoin node exposes three classes of HTTP endpoints:

1. **Consensus endpoints** (`/info`, `/block/*`, `/tx` broadcast, `/balance/*`,
   `/utxos`, `/mempool`, …) — always open. Reads are public data; `POST /tx`
   is self-authenticating (a transaction carries its own signatures).
2. **App-layer reads** (`/api/tokens`, `/api/usernames`, invoices status, …) —
   always open.
3. **App-layer writes** (create invoice/token/username/webhook/escrow, …) —
   require a **developer API key** when the operator sets
   `NETCOIN_APP_REQUIRE_API_KEY=1` (the hosted relay runs with it on).
   Community posts/reports/improvement votes keep their public carve-out.

## Developer keys

- `POST /api/keys/register` (open, no auth) returns a free key:
  `{"api_key": "nck_…"}`. Only the SHA-256 hash is stored server-side.
- Send it as the `X-Netcoin-Api-Key` header (or `api_key` body field).
- Registration is capped per IP per day; per-IP/per-endpoint request rate
  limits still apply on top.
- The official sites auto-register a key per browser (see `site-shell.js`),
  so normal users never see any of this.
- Merchant-scoped keys with permissions (`/api/merchant/api-keys`) continue to
  work and additionally satisfy the write gate.

## Explicit limitation (documented on the Tokens pages)

An API key identifies *an app*, not *a coin owner*. App-layer state that
references addresses (tokens, usernames) is **not** protected by chain
signatures: anyone with a key may call, for example, a token transfer for any
account. Signature-bound app-layer writes (a signed-message envelope proving
control of the `from` address) are the planned follow-up and will be specified
in a future NIP before app-layer balances should be treated as anything more
than demo/loyalty accounting.
