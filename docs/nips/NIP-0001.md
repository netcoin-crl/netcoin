## What a NIP is

A NIP (NetCoin Improvement Proposal) is a short design document for any change
that other people must coordinate around: consensus rules, P2P protocol,
wallet-safety standards, app-layer API standards, or economics. Pure
implementation details (refactors, UI copy, bug fixes) do not need a NIP.

The NIP process is also **the place to say "no" or "later"**: anything on the
ROADMAP.md research shelf (VMs, privacy cryptography, bridges, on-chain account
abstraction) stays there until a NIP makes the case that it is safe to build.

## Ground rules (inherited from ROADMAP.md)

1. **One excellent core, clearly-labeled optional rooms.** Consensus changes are
   rare and must be small, reviewable, and activation-gated.
2. **The turn-it-off test.** A feature that breaks simple Send / Receive /
   Balance when disabled is in the wrong layer and will not be accepted as an
   app-layer NIP.
3. **Risk colors decide the bar.** 🟢 app/UI (no NIP needed unless it defines a
   standard), 🟡 wallet/infra (NIP for anything security-sensitive), 🔴
   consensus/core-crypto (NIP always, plus tests, plus an upgrade window).

## Lifecycle

`Draft → Review → Accepted → Active` (or `Rejected` / `Withdrawn` / `Superseded`)

- **Draft**: a file under `docs/nips/NIP-XXXX.md` using the header table above,
  submitted as a pull request.
- **Review**: discussion on the PR. For consensus changes the PR must include
  tests and state the proposed activation height (see NIP-0005).
- **Accepted**: merged with status Accepted; implementation may land behind an
  activation gate.
- **Active**: the change is live on the public testnet (past its activation
  height, or deployed for non-consensus NIPs).

## Numbering

Numbers are assigned in the index in ROADMAP.md. 0001–0009 are reserved for
process and safety standards.
